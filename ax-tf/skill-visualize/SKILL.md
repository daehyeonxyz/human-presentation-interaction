# 스킬 설명 시각화

스킬을 처음 보는 임직원이 한 장만 보고 언제 쓰는지, 뭐라고 요청하는지, 무엇을 받는지 알게 하는 설명서를 만든다. 왼쪽은 스킬 이름과 상자 세 개(이럴 때 씁니다 / 이렇게 해 줍니다 / 파일 구성), 오른쪽은 Claude 채팅창으로 실제 요청과 결과를 보여 준다. 화면은 고정이고 `content.json` 만 채운다.

## 파일

```text
assets/template.html       1920×1080 화면. 데이터만 바뀌고 배치는 고정
scripts/build.py           content.json 을 넣어 HTML 을 만들고 칸별 글자 수를 검사
references/content-guide.md  칸별 작성 기준과 글자 수 상한
examples/                  사내 스킬 4종의 예시 (json, html, png). 칸 채우는 법은 json 을 본다
```

## 절차

1. **대상 스킬 읽기**
   - 첨부된 스킬 폴더나 zip 을 풀어 `SKILL.md` 전문과 파일 목록을 읽는다.
   - 스킬이 다른 파일을 참조하는데 패키지에 없으면 그 사실을 기록해 둔다. 설명서의 파일 구성에는 실제로 있는 파일만 넣는다.

2. **내용 뽑기**
   - `references/content-guide.md` 를 읽고 칸마다 들어갈 내용을 정한다.
   - 모든 문장의 근거는 대상 스킬의 SKILL.md 와 파일이다. 스킬에 없는 기능이나 수치를 지어내지 않는다.
   - 먼저 스킬의 본질을 한 문장으로 정한다. 사용자가 이 스킬로 실제로 얻는 것이 무엇인지다. SKILL.md 의 첫 문단이나 description 앞부분만 보고 정하지 않는다. 절차 전체를 읽고 어느 경로가 기본이고 어느 경로가 대안인지 가른다.
     - 예: knox-email 은 description 이 "2주 보관 한도에 걸리기 전에 보관한다"로 시작하지만, 기본 경로는 Knox Desktop 이 PC 에 이미 저장한 메일을 Claude 가 찾아 읽는 것이고 웹메일 보관은 Knox Desktop 이 없을 때의 대안이다.
   - "이렇게 해 줍니다"는 description 이 아니라 사용자 흐름으로 쓴다. 사용자가 무엇을 넣고 무엇을 받는지가 기준이다.
     - 산출물이 여럿이면 `does_lead` 한 줄로 전체를 말하고, 그 아래 항목을 산출물별로 쓴다(예: deal-sourcing 은 기술 실사 브리프 HTML, 1페이저 Word, 소분과 덱 PPT).
     - 항목 수는 내용에 맞춘다. 네 칸을 채우려고 내부 절차를 끼워 넣지 않는다.
     - 검증 통과(`QA: PASS`), 글자 수 검사, 스크립트 이름처럼 사용자에게 보이지 않는 내부 동작은 쓰지 않는다.
   - 제목과 "이렇게 해 줍니다"의 앞 항목은 기본 경로로 쓴다. 대안 경로는 한 줄로만 넣는다.
   - 실행 환경 제약(특정 탭에서만 동작, 설치가 필요한 프로그램)이 있으면 반드시 넣는다. 읽는 사람이 엉뚱한 곳에서 부르지 않게 하기 위해서다.
   - 채팅 예시는 기능 시연이 아니라 실제 사용 장면(use case)으로 고른다. 읽는 사람이 "내가 이 스킬을 쓰기 시작하는 순간"을 알아보게 하는 것이 목적이다.
     - 사용자 흐름이 시작되는 순간을 그대로 옮긴다. 그 일을 할 때 손에 있는 자료를 첨부하고(`attach`), 업무 맥락을 한 문장으로 말한다.
       - 좋은 예: 피치덱 PDF 를 첨부하고 "이 업체 새로 투자했어. 담당 심사역은 홍길동이야"
       - 좋은 예: "지금 관심사 리스트 엑셀로 줘 봐" 로 받은 뒤, 고친 엑셀을 첨부하고 "새로 업데이트한 거랑 합쳐서 다시 넣어 줘"
       - 나쁜 예: "B 업체 추가해 줘", "키워드에 HBM 넣어 줘"처럼 스킬 기능 이름을 그대로 부르는 문장
     - 첨부 파일 이름은 실무에서 쓰는 이름처럼 쓴다(예: `B사_IR덱_2026.pdf`, `4팀_관심사_1022.xlsx`).
     - 흐름이 여럿이면 한 채팅에 몰지 않고 장면별로 나눈다. 한 장의 채팅은 장면 하나다.
     - 요청 문장에는 스킬 description 의 트리거 표현을 살리되, 위 장면 안에서 자연스럽게 나오게 한다.
   - 스킬이 파일을 만들면 채팅에 결과물 미리보기를 넣는다. 결과가 채팅 답으로 나오는 스킬(찾기, 요약, 질의응답)은 미리보기 없이 답 본문을 `md` 로 채팅 안에 보여 준다. 보고서 같은 문서 결과물이면 SKILL.md 안의 예시 문장으로 종이(`lines`)를 그린다. md 파일 결과물이면 `style: "md"` 로 노션처럼 렌더링한다. 화면·이미지 결과물이면 결과 이미지(`image`)를 넣는다. 파일 결과의 이미지가 없고 만들 수도 없으면 결과의 첫 몇 줄을 `lines` 로 보여 준다.

3. **사용자 확인**
   - 스킬 이름(제목)과 채팅 예시 흐름(메시지 순서와 요청 문장)을 먼저 보여 주고 확인받는다.
   - 스킬 이름은 사람들이 부를 짧은 한국어 이름이다(예: `삼성 양식 보고서 작성`). 사용자가 이름을 정해 주면 그대로 쓴다.
   - 수정 요청이 있으면 반영해서 다시 확인받는다.

4. **조립**
   - `content.json` 을 작성하고 `python scripts/build.py content.json <스킬이름>-설명서.html` 을 실행한다. Windows 는 `python`, macOS·Linux 는 `python3` 이다.
   - 넘치는 칸이 출력되면 그 문장을 줄여 다시 실행한다. 통과할 때까지 반복한다. 글꼴 크기나 레이아웃을 바꿔서 맞추지 않는다.

5. **전달**
   - 만든 HTML 파일을 전달한다. 브라우저에서 열어 전체 화면으로 보거나 캡처해서 메일에 붙인다.
   - 이 환경에서 브라우저(playwright 등)를 쓸 수 있으면 1920×1080 PNG 도 함께 만든다. 쓸 수 없으면 HTML 만 전달하고 그 사실을 알린다.
   - 2단계에서 기록한 누락 파일이 있으면 함께 알린다.

## 문장 기준

- 왼쪽 상자의 항목은 명사형이나 짧은 평서문으로 끝낸다. 마침표를 찍지 않는다.
- 과장 수식(획기적·강력한·완벽한)과 비유를 쓰지 않는다.
- 같은 내용을 두 상자에 반복하지 않는다. "이럴 때 씁니다"는 상황, "이렇게 해 줍니다"는 스킬이 하는 일이다.
- 채팅 예시는 실제 대화처럼 자연스럽게 쓴다. 사용자 문장은 평소 입력할 법한 반말 요청("~좀 써 줘", "응, 그렇게 해 줘")이고, Claude 문장은 부드러운 "~요" 존댓말("괜찮을까요?", "작성했어요")이다. "~드립니다", "통과한 ~입니다" 같은 보고서 말투는 쓰지 않는다.
- 채팅의 목록 항목도 말하듯 쓴다("제목은 '○○'", "비교표 하나 추가"). "제목: ○○" 같은 라벨식 표기는 쓰지 않는다.
- 파일 이름, 사람 이름, 수치를 예시로 넣을 때는 스킬 안에 있는 것을 쓴다. 없으면 일반적인 이름(예: `회의록_1020.docx`)을 쓴다.

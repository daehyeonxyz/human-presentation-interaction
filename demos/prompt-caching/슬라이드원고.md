# 프롬프트 캐싱과 비용 — 슬라이드 원고

인쇄 층의 단일 원본이다. 구현은 이 글자를 앉히기만 하고 새 문장을 만들지 않는다. 강조 낱말은 굵게 표시한다.

## 1쪽 표지 (cover-stage)

- 제목: 프롬프트 캐싱과
  비용 (두 줄. 줄 나눔은 이 표기가 정본이다)
- 태그라인: 같은 앞부분을 다시 보내지 않는 법
- 오른쪽 위 영문: PROMPT CACHING
- 오른쪽 아래 영문: human-presentation-interaction demo deck 02

## 2쪽 (pick-list)

- kicker: COST
- 제목: 비용은 **세 곳**에서 쌓인다
- 부제: Input · Output · Repetition
- 항목 1 이름: 입력 토큰
- 항목 1 펼침: 시스템 프롬프트와 도구 정의와 지난 대화 전부가
  요청마다 입력으로 다시 들어간다
- 항목 2 이름: 출력 토큰
- 항목 2 펼침: 모델이 새로 만든 글자. 단가가 입력보다 높다
- 항목 3 이름: 반복 전송
- 항목 3 펼침: 대화가 길어질수록 같은 앞부분을
  매번 다시 보내는 비중이 커진다
- 맺음: 반복 전송이 커지는 구조가 캐싱이 노리는 **표적**

## 3쪽 (drag-compare)

- kicker: CACHE
- 제목: 캐시는 요청의 **앞부분**을 저장한다
- 부제: Without cache · With cache
- 왼쪽 화면 이름: 캐시 있음
- 오른쪽 화면 이름: 캐시 없음
- 공통 구간 라벨: 시스템 프롬프트 / 도구 정의 / 지난 대화 / 새 질문
- 캐시 없음 쪽 구간 표기: 전부 입력 단가 (예시 100%)
- 캐시 있음 쪽 구간 표기: 저장된 앞부분은 캐시 단가 (예시 10%) 새 질문만 입력 단가
- 맺음: 핸들을 끌어 보면 두 요청의 차이는 **앞부분의 단가**뿐

## 4쪽 (input-sandbox)

- kicker: HIT
- 제목: **같은 접두사**로 보내야 적중한다
- 부제: Prefix match
- 입력 칸에 차오를 요청 후보 (전송 버튼으로 차례대로 재현):
  - 요청 1: 어제 회의록을 요약해 줘
  - 요청 2: 요약에서 결정 사항만 뽑아 줘
  - 요청 3: (시스템 프롬프트를 바꾼 뒤) 결정 사항을 표로 만들어 줘
- 관찰 창 머리: 요청의 구성
- 관찰 창 구간 라벨: 캐시 적중 / 새로 계산
- 관찰 창 해설 1: 첫 요청. 저장된 것이 없어 전부 새로 계산
- 관찰 창 해설 2: 앞부분이 같아 적중. 새 질문만 계산
- 관찰 창 해설 3: 앞부분이 바뀌어 적중 실패. 전부 새로 계산
- 맺음: 적중의 조건은 내용이 아니라 **글자 그대로 같은 접두사**

## 5쪽 (drag-threshold)

- kicker: RATE
- 제목: **적중률**이 비용을 정한다
- 부제: Hit rate · Input cost
- 슬라이더 이름: 캐시 적중률
- 게이지 이름: 하루 입력 비용 (예시)
- 기준 표기: 적중 0%면 100 / 적중 100%면 대략 10 (예시)
- 곁 문장: 적중률은 운이 아니라 설계가 정한다
  자주 바뀌는 것을 뒤로 보내면 접두사가 안정된다
- 맺음: 비용 절감은 모델 선택보다 **요청 구조**에서 먼저 나온다

## 6쪽 정리 (accumulate-recap)

- kicker: RECAP
- 되짚기 항목: 반복 전송 / 앞부분의 단가 / 글자 그대로 같은 접두사 / 요청 구조
- 선언: 캐싱은 할인이 아니라 **설계**다
- 다음 물음: 우리 요청에서 매번 다시 보내는 앞부분은 몇 토큰일까

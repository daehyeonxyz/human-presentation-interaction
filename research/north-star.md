# 지향점 (north star) — "Explore the context window" 해부

2026-07-25 사용자 확정 지향점. 레퍼런스는 Claude Code 공식 문서(code.claude.com/docs)의 인터랙티브 위젯 "Explore the context window"다. 이 스킬이 만들 인터랙션의 품질 기준이자, 무엇이 "도형 몇 개"와 "진짜 구현체"를 가르는지의 실물 표본이다.

사용자 원문 요지: 컨텍스트 윈도우라는 개념을 설명할 때 그냥 도형 몇 개가 아니라, 어떤 인터랙션이 필요할지(간단하면 되는지 복잡해야 하는지) 고민하고, 디자인·레이아웃·실을 예시와 개념·단계와 인터랙션을 고민해서, 실제 웹에서 인터랙티브하게 구동되는 구현체를 깊은 사고로 만들어내는 것까지가 지향점이다.

## 레퍼런스가 하고 있는 일 (관찰)

화면 구성 (1920 기준 관찰):

- 왼쪽 위 제목 "Explore the context window" + 한 줄 설명 "A simulated session showing what enters context and what it costs"
- 오른쪽 위 라이브 지표 "~7.8K tokens / 200K · illustrative" — 시뮬레이션 진행에 따라 실시간 갱신
- 제목 아래 컨텍스트 윈도우 누적 바 — 카테고리별 색 세그먼트가 차오르는 상태 시각화 + 색 범례 11종 (System, CLAUDE.md, Memory, Skills, MCP, Rules, You, Files, Output, Claude, Hooks)
- 눈 아이콘 범례 "= appears in your terminal" — 보이는 것과 안 보이는 것의 구분 자체가 콘텐츠
- 중앙 이벤트 로그 — "BEFORE YOU TYPE ANYTHING" 아래 auto 뱃지 항목들이 토큰 비용(+4.2K, +680, ...)과 미니 바를 달고 순서대로 쌓임 → "YOU TYPE IN YOUR TERMINAL" 프롬프트 입력 재현
- 오른쪽 인스펙터 패널 — "Hover to preview. Click to pin so you can scroll." 안내. 항목에 호버하면 미리보기, 클릭하면 고정. 고정된 카드는 제목·뱃지(Auto-loaded)·토큰 수·설명·보조 카드(Invisible in your terminal / Save context 팁)로 계층화
- 하단 컨트롤 — 재생 버튼, 스크럽 가능한 진행 바(0%~100%), 전체화면 버튼
- 초기 상태는 빈 터미널과 "Start session" 버튼 하나 — 시작 전에도 화면이 스스로 설명됨

## 왜 이것이 "도형 몇 개"가 아닌가 (원리 추출)

1. **인터랙션이 곧 논증이다.** 이 위젯의 핵심 메시지("입력하기 전에 이미 많은 것이 로드된다")는 텍스트로 주장되기 전에 시뮬레이션으로 체험된다. 재생을 누르면 토큰 카운터가 차오르는 것을 보는 행위 자체가 증명이다. 인터랙션은 장식이 아니라 메시지의 전달 수단이다.
2. **체험 뒤에 언어로 못박는다.** KEY TAKEAWAY 카드가 방금 본 것을 문장으로 고정한다. 인터랙션과 해석 텍스트는 대체 관계가 아니라 역할 분담이다.
3. **상태·시퀀스·상세의 3층 정보 구조.** 항상 보이는 전역 상태(누적 바 + 카운터), 시간 순서(이벤트 로그 + 재생), 요청 시 상세(호버 미리보기 → 클릭 고정)가 분리돼 있다. detail-on-demand가 설계돼 있어 화면이 한 번에 다 말하려 들지 않는다.
4. **조작 문법을 화면에 명시한다.** "Hover to preview. Click to pin so you can scroll."처럼 어포던스를 문장으로 적는다. 청중도 발표자도 헤매지 않는다.
5. **통제권이 있다.** 재생·스크럽·전체화면. 발표자는 임의 지점으로 건너뛸 수 있고, 시뮬레이션이 발표를 끌고 가지 않는다.
6. **구체 수치로 말한다.** 추상 도형이 아니라 +4.2K, +680, 1.8K tokens 같은 그럴듯한 실측형 예시. 동시에 "illustrative"라고 정직하게 표기한다.
7. **콘텐츠 설계가 인터랙션 설계다.** 어떤 이벤트를 로그에 넣을지, 어떤 항목에 어떤 설명 카드를 붙일지, 어디서 끊어 단계로 만들지가 전부 내용 결정이다. 인터랙션 뼈대만 만들고 내용을 붓는 것이 아니라, 내용의 논리 구조가 인터랙션 구조를 결정한다.

## 인터랙션 복잡도 사다리 (스킬의 판단 축)

개념마다 "어떤 인터랙션이 필요한가"를 먼저 판정한다. 복잡도는 메시지가 요구할 때만 올린다.

| 단계 | 형태 | 언제 |
|---|---|---|
| 0 정적 | 잘 설계된 다이어그램·표 | 구조가 정지 상태로 다 보일 때 |
| 1 공개 | 호버 공개·클릭 팝업·토글 | 상세를 숨겨 인지 부하를 줄일 때 (detail-on-demand) |
| 2 단계 | fragment 진행·상태 전환·비교 슬라이더 | 변화·대비·과정이 메시지일 때 |
| 3 시뮬레이션 | 재생 가능한 모델 + 탐색 + 인스펙터 | 시스템의 동작 자체가 메시지일 때 (레퍼런스가 여기) |

판정 질문: 이 페이지의 핵심 메시지는 정지 화면으로 증명되는가, 변화를 보여야 하는가, 체험시켜야 하는가.

## 앵커링 경계 (사용자 확정)

- growth-ppt는 삭제됐다. 이 프로젝트는 그 후계가 아니라 더 좋은 방향의 신규 설계다.
- `design-decks`·`labsem-ppt`는 앵커가 아니다. 정적 슬라이드 생성기의 절차·미감·템플릿을 기본값으로 끌어오면 지향점(구현체 수준의 인터랙션)이 하향 앵커링된다. 개별 부품(고정 스테이지 스케일링 CSS 같은 검증된 역학)을 의식적으로 골라 쓸 수는 있으나, 절차·스타일·구성 관행은 이 레포가 스스로 정의한다.
